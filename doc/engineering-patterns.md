# エンジニアリングパターン集

> プロジェクト横断で効く落とし穴（gotcha）と定石を集約する。DDアーカイブ時に
> 「この知見は半年後の別の作業でも効くか？」で判定し、効くものをここへ昇格させる。
> 詳細は元DDが正本。ここは「再発防止のための気づきポイント」。

## 昇格の基準

| 昇格する | 昇格しない（DD本体に残すだけでよい） |
|---------|----------------------------------|
| DAで見つかった「同根パターン」（同じ罠が複数箇所にある） | そのDD限りの一回性の問題 |
| 言語・フレームワークの仕様に起因する罠（再発確実） | 実装中に自然に気付くレベルの規約 |
| 「正しいやり方」が自明でなく、毎回調べ直しになる定石 | Lintルール化できたもの（→ `lint-fix-hints.json` へ） |

## 書き方

1パターン = 1セクション。「症状 → 原因 → 正しいやり方 → 元DD」を5〜10行で。
コード例は ❌/✅ の対比で最小限に。

## 1. `http.server.HTTPServer` + フロント側`Promise.all`でハングする

- **症状**: フロントエンドで`Promise.all([fetch(A), fetch(B)])`のように複数APIを並行取得
  するよう変更したら、2つ目以降のリクエストが返らずページが固まる。単体でcurl等から
  同じエンドポイントを叩いても同様にタイムアウトする。
- **原因**: `http.server.HTTPServer`はシングルスレッドで、1つの接続を処理し終えるまで
  次の接続をacceptしない。ブラウザがKeep-Alive接続を維持したまま次のリクエストを待つ間、
  サーバーのメインループがブロックされ続け、別の接続（並行fetchのもう一方）を永遠に
  処理できなくなる。ページロードが常に1リクエストのみだった間は表面化しない。
- **正しいやり方**:

```python
❌ from http.server import HTTPServer
   server = HTTPServer(("localhost", port), Handler)

✅ from http.server import ThreadingHTTPServer
   server = ThreadingHTTPServer(("localhost", port), Handler)  # リクエストごとにスレッドを立てる
```

- **元DD**: DD-002-1

## 2. クリック可能な要素を`<div onclick>`だけで作るとアクセシビリティツリーに現れない

- **症状**: 統計カード等をクリック可能にしたが、自動操作ツール（`find`等）で要素を探しても
  見つからない。Tab+Enterのキーボード操作でも反応しない。
- **原因**: ネイティブのクリックハンドラだけを持つ`<div>`はアクセシビリティツリー上では
  ただの汎用要素として扱われ、インタラクティブ要素として認識されない。
- **正しいやり方**:

```html
❌ <div onclick="toggle()">...</div>

✅ <div role="button" tabindex="0" onclick="toggle()"
      onkeydown="if(event.key==='Enter'||event.key===' ')toggle()">...</div>
```

- **元DD**: DD-002-4

## 3. `window.prompt()`/`window.confirm()`は自動操作ブラウザで使えない

- **症状**: 自動操作ブラウザ（Claudeの組み込みブラウザ等）で画面を検証すると、
  `window.prompt()`/`confirm()`を呼んだ瞬間に「not supported」エラーとなり後続処理が止まる。
- **原因**: 自動化・ヘッドレス系のブラウザ環境ではネイティブダイアログAPIがサポートされない
  ことがある。
- **正しいやり方**: ページ内で完結する入力UI（クリックでその場に展開するフォーム等）に
  置き換える。確認操作も同様にページ内UIで代替し、ネイティブダイアログに依存しない。
- **元DD**: DD-003, DD-004

## 4. 複数のデータ再読み込み経路があると、UI状態のリセット漏れが起きやすい

- **症状**: 列ソート等の状態を持つ画面で、モード切替・ファイルアップロード・外部接続など
  「データを読み直す」操作のうち1つだけがリセット処理を呼び忘れ、見た目（矢印表示等）と
  実データが食い違う。
- **原因**: 読み込みのエントリポイントが共通の読み込み関数の外側に複数存在する設計だと、
  1箇所を直しても他の箇所を見落としやすい。
- **正しいやり方**: 「データを読み直す全操作」を先に列挙してから横断的にリセット処理の
  有無を確認する。可能なら状態リセットを共通の読み込み関数の内側に寄せ、経路を1つにする。
- **元DD**: DD-009

## 5. `export_static.py`は`INDEX_HTML`の文字列置換に依存しており、構造変更に弱い

- **症状**: `web_viewer.py`の`load()`関数の中身を変えただけなのに、`export_static.py`が
  生成する静的HTMLが壊れる（編集系UIが残って表示されてしまう等）。
- **原因**: `export_static.py`は`INDEX_HTML`文字列中の`load()`関数本体を文字列操作で丸ごと
  置換して`EMBEDDED_DATA`を埋め込む設計。置換対象の関数の構造が変わると追従できない。
- **正しいやり方**: `web_viewer.py`の`load()`まわりを変更したら、`pytest
  tests/test_export_static.py`だけでなく実際に`export_static.py`を実行した出力も確認する。
- **元DD**: DD-003

## 6. Dr.Sumの`__all_tables__`は`assortment='table'`（見出し行）と`'column'`（カラム詳細）が別行

- **症状**: `assortment='table'`で絞り込んでSELECTすると、`column_name`等がすべて`NULL`に
  なる、またはテーブルが1件しか列を持たないように誤認する。
- **原因**: `'table'`は1テーブルにつき1行だけのテーブル自体の見出し行でカラム情報を持たない。
  実際のカラム詳細（`column_name`/`column_type`等）は`'column'`側に1行1カラムで格納されている。
- **正しいやり方**: カラム一覧を取得するクエリは`assortment='column'`で絞り込む。
- **元DD**: DD-002-2

## 7. ZIP内エントリ名の日本語がPython既定デコード（cp437）で文字化けする

- **症状**: 日本語ファイル名を含むZIP（MotionBoardの内部コンテンツストア`.fs-file`等）を
  Pythonの`zipfile`で素朴に読むと、エントリ名が文字化けして目的のファイルを特定できない。
- **原因**: ZIP仕様上UTF-8フラグが立っていない場合、Pythonの`zipfile`は既定で
  cp437（IBM PC）としてファイル名をデコードする。
- **正しいやり方**: `info.filename.encode("cp437").decode("shift_jis")`のように、
  実際に想定されるエンコーディングへ再デコードする。
- **元DD**: DD-002-3

## 8. `INDEX_HTML`(Python三重引用符文字列)内のJSで`\n`等のエスケープを書くと、Python側で先に解釈されて壊れる

- **症状**: `web_viewer.py`の`INDEX_HTML`に埋め込まれたJSで`'\n'`のように書くと、ブラウザで
  `Uncaught SyntaxError: Invalid or unexpected token`になる。
- **原因**: `INDEX_HTML = """..."""`は生文字列(`r"""`)ではない通常のPython文字列なので、
  Pythonパーサが`\n`を実際の改行文字として解釈してしまう。結果、JS側の単一引用符文字列
  `'...'`の途中に生の改行が入り込み、JS構文として壊れる(テンプレートリテラルも同様)。
- **正しいやり方**: JS側で`\n`等のエスケープシーケンスをそのまま出力したい場合は、Python
  ソース上で`\\n`(二重バックスラッシュ)と書く。既存の`normalizeKey`の`"\\u0000"`も同じ対策。
  この種の編集後は`pytest`だけでなく実際にブラウザで開いてconsoleエラーが無いか確認する
  (Pythonの構文チェックは通ってしまうため、pytestだけでは検出できない)。
- **元DD**: DD-018

## 9. 汎用ヒューリスティック(`LABEL_KEY_HINTS`、または「同一要素内の他属性探索」)は、物理カラム名と無関係な概念も「カラムのエイリアス」と誤認する

- **症状**: `board_parser.py`の自動検出モードで、MotionBoard上では一度もエイリアスを設定して
  いない物理カラムに対して、実在しない表示名(例: 絞り込み用プリセットフィルタのラベル、
  集計表の別の軸のラベル、無関係なフラグ値)がエイリアスとして検出される。
- **原因**: `auto_parse_xml`の汎用ヒューリスティック(`walk()`)は、ある要素の属性値が
  物理カラム名と一致すると、**同一要素内の他の属性**からラベル候補を機械的に探す
  (`find_label_on_element`)。この時、「物理カラム名と一致した属性」と「ラベル候補として
  拾う属性」の間に意味的な関連性を一切検証していないため、以下のような誤検出が起きる:
  - 属性名ベースの誤検出: `LABEL_KEY_HINTS = ("label", "disp", "name", "alias", "title",
    "caption", "表示", "名称")`に部分一致する属性名を無条件にラベル候補として優先する。
    MotionBoardの検索条件(`<SearchCondition><PreCondition><Expression title="<列名>"
    dispTitle="<条件のキャプション>">`)は`dispTitle`属性名が`"disp"`にヒットしてしまうため、
    「このカラムをどう絞り込むか」のラベルを「このカラムをどう表示するか」のエイリアスと
    取り違える(DD-023)。
  - 要素構造ベースの誤検出: 集計表(クロス集計)パーツの軸設定`<ItemOrderChange
    category="<行軸列名>" series="<列軸列名>" summary="<集計値列名>">`は、無関係な3つの
    フィールド参照を同一要素の属性として同居させる。行軸の列名と一致した後、
    `LABEL_KEY_HINTS`に一致する属性名が無ければ「日本語を含む最初の属性値」
    (＝列軸・集計値側の列名)にフォールバックしてしまう。子要素`<Item label="<列名>"
    data="<列名>" selected="true" fid="...">`では`label`/`data`が値一致で除外され、
    残る`selected="true"`が最終フォールバックで採用され、`true`という不自然な値が
    エイリアスとして記録される(DD-027)。
  データソース定義専用パーサー(`_parse_drsum_datasource`)はこの経路を通らないため
  影響されないが、ボード本体XML(`<DataSource type="drsum">`を持たないファイル)は
  汎用ヒューリスティックの対象になる。
- **正しいやり方**: `LABEL_KEY_HINTS`に新たにヒットしそうな属性名を見つけたら、それが
  「表示名の定義」なのか「表示名によく似た別の概念(絞り込み条件・並び替え条件・集計軸の
  ラベル等)」なのかを、実機のXML構造で確認してから採用する。後者と判明した場合は属性名で
  判定するのではなく、祖先要素のタグ名(例: `SearchCondition`/`PreCondition`/`Expression`/
  `ItemOrderChange`)で該当サブツリーごと`walk()`の対象から除外する
  (`NON_ALIAS_CONTEXT_TAGS`+`_in_non_alias_context()`のパターン)。同じ欠陥クラスの
  新しいタグが見つかった場合は、個別の定数・関数を増やすのではなく
  `NON_ALIAS_CONTEXT_TAGS`にタグ名を追加して一箇所に集約する。
- **元DD**: DD-023, DD-027
